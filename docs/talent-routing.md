# 人才入库与职能分流 V1

2026-11-14。第一轮识别人才适合进入哪些职能方向，第二轮才针对具体岗位研究和初筛。没有进入前端列表的后端人才不会被记为不合格；无相关岗位、方向不明、提取失败的人仍保留在人才库。本版没有引入向量数据库或向量模型。

## 流程与实际范围

批量上传 → 一次 A04 完整简历提取及多标签分类 → 独立人才档案 → 与已发布岗位的方向标签关联 → 待深度初筛 → 显式启动 A03 → A05。

人才入口不要求岗位存在，也不要求先发布规则。岗位候选关系沿用当前 Application 与 RulePack，只有岗位启用、规则已发布且执行模式一致时才建立。分类不检查具体岗位的年限、学历、薪资、胜任程度，不生成 D06 或电话交接。后续正式初筛达标仍按既有规则自动登记交接，不新增人工拨号触发步骤。

同一人才可关联多个岗位，`candidate_id` 保持为人才 ID，`application_id` 按岗位分别生成。A04 模型只调用一次，结构化内容复用；为遵守现有岗位权限和产物合同，每个关联保存自己的原始文件引用、证据与 D03 快照。D03 记录 `talent_profile_ref={talent_id,version}`，不会为每个岗位重复调用提取模型。本版尚未跨岗位复用 A03 的研究执行结果。

## 分类口径

方向目录为版本 1，涵盖前端、后端、全栈、移动端、数据、算法、运维、测试、产品、设计、销售、营销、运营、财务、人力、法务、供应链、硬件。它是可扩展的工程目录，不是完整职业标准。

真实模式由 A04 同时输出 `direction_assignments`：方向 ID、primary/secondary、连续原文 quote、分类理由。结合本人职责和技能使用场景判断；不能因简历出现 React 就当作主要从事前端，不能把“管理后台页面”当作后端服务经历。缺失或不在简历中的分类引文被丢弃，没有可靠分类则保持待分类。代码校验引文存在，不能保证分类语义一定正确，仍需人工样本评测。

全栈标签可路由到前端、后端或全栈岗位；单独的前端或后端标签不会自动推断全栈能力。没有打标签的岗位不会吸收全部人才。新岗位的明确职能名称可产生初始方向建议，猎头可以通过岗位 PATCH 修改、清空；这里只使用岗位名称归一，不把 JD 中偶然提及的工具作为岗位方向。

人工修订分类需提交期望 revision、原文依据和理由，生成 TalentProfile 新版本。尚未开始研究的岗位关联随新分类更新：不再相关的关联转 `routing_inactive`，从当前列表移出，初筛结果仍为 pending；再次相关时复用同一关联。已经开始的研究保留原输入快照，不因纯职能标签变化重拨、重算或重新交付。简历事实更正仍走既有 D03 更正与失效传播入口，不用标签修订冒充事实修正。

## HTTP 接口

沿用同一会话、Origin、CSRF、业务 POST 幂等和分页协议。机构与所有者来自登录会话。只允许访问本人可见的人才及岗位；同机构其他用户也不可直接读取。

| 接口（前缀 `/api/v1`） | 行为 |
| --- | --- |
| `GET /talent-directions` | 方向目录及版本 |
| `POST /talent-imports` | JSON 文本或 multipart 文件批次，逐份 accepted/duplicate/invalid 回执 |
| `GET /talents` | 人才分页，支持姓名 q；包含无关联、未分类与提取失败的人才 |
| `GET /talents/{id}` | 提取内容、分类、任务状态和相关岗位 |
| `GET /talents/{id}/file` | 受权限保护的原始简历 |
| `PATCH /talents/{id}/directions` | 保存人工分类新版本并更新尚未开始的关联 |
| `POST /talents/{id}/route` | 按当前标签重新关联，不重复提取、研究或创建已有关系 |
| `PATCH /jobs/{id}` | 新增 routing_directions 字段；修改、恢复启用时更新待处理关联 |
| `POST /jobs/{id}/rules/publish` | 规则发布后关联库中已有的相关人才 |
| `POST /applications/{id}/start-screening` | expected_revision 与 reason，202 返回真实持久化 research 任务 |
| `GET /tasks/{id}`、`POST /tasks/{id}/retry` | 复用任务查询和受控内部恢复；新增 talent_parse 类型、talent 资源类型 |

创建岗位也可显式提供 `routing_directions`。机器可读字段、枚举与错误以 `docs/api/openapi.implemented.v1.json` 为准。

同一所有者、相同文件内容和执行模式只提取一次；同名但不同文件不自动合并个人身份。真实与模拟分别去重，不能用模拟档案驱动真实规则。受限档案不可通过重放上传恢复，也会阻断关联文件、产物、列表和 worker 读取。与旧岗位上传产生的相同文件关联不自动合并身份，需要单独核对。

提取复用已有执行租约、资源指纹、模型预算与响应账本。人才任务没有伪造岗位，`Task.job_id=null`。旧预算/用量表的 `job_id` 列在此路径作为内部预算 scope，使用 `talent:{id}`；浏览器通过人才归属校验后才能查询。每份人才提取最多一次模型提交；已知响应可恢复内部保存，外部结果不明保持 reconciling，不自动再次提交。任务的 result_refs 不伪造岗位产物；由 resource_type=talent、resource_id 和人才 profile_version 定位结果。

## 数据库与页面

新增显式迁移 `0004_talent_routing`，创建 talents、talent_profiles，并增加岗位方向、关联来源和任务可空岗位字段。API/worker 不在启动时建表。已有岗位、规则、简历与历史产物保留；本版不自动把旧 Application 合并为人才身份。存在人才任务时降级会拒绝，不删除材料来迁就旧表结构。

登录后的“人才库”及全部简历上传按钮使用新入口，支持 TXT、文本 PDF、DOC/DOCX。人才页查看分类依据、修订方向和相关岗位；岗位候选人页设置方向、显示待深度初筛与后续结果，从详情启动研究。刷新从服务端恢复人才档案；浏览器隐藏时暂停页面轮询。未登录预览保留原有隔离演示，不提交真实材料。

人才列表只显示“候选人／适配岗位／查看信息”三列。“适配岗位”读取 `TalentView.applications[].job_id/job_title`，展示导入提取及职能分流建立的全部当前有效岗位关联；按岗位 ID 去重，同名不同岗位保留，不按后续初筛通过与否过滤，不在浏览器另做关键词匹配。后端仍按启用状态、正式规则发布状态、执行模式和可见权限决定关联；列表文案不改变这些边界。提取中无结果显示“匹配中”，已分类但无关联显示“暂无适配岗位”。分类及初筛进度保留在档案和岗位详情中，列表不显示初筛结论或规则版本。

未登录列表使用独立的 `Candidate.matchedJobIds` 预览字段，样例匹配关系由资料显式提供；`jobId` 继续表示已有下游流程绑定的岗位，不能作为没有匹配结果时的回退。预览中的岗位筛选和搜索遍历全部适配岗位，三个查看入口与返回后保留列表条件的行为保持。

岗位列表及其人工编辑、发布仍受现有前端交付范围限制：本机保存的岗位标准不等于正式后端 RulePack 已发布。新候选人页以服务器 rule_status 为准，未正式发布就明确等待，不将本机发布视为业务授权。该既有发布对接尚未在本次扩展为完整前端规则编辑器。

旧 `POST /jobs/{id}/resume-batches` 保持原先“指定岗位后直接进入研究与初筛”的兼容行为，供已有接入使用；新的登录页面不再使用它。内部 A/B 1.1 交接事件不变，新增分流阶段不会发布 screening.passed。

## 岗位候选人状态与退出

岗位下的候选人队列使用以下三种前端展示状态，人才库的全部人才及适配岗位不受此过滤影响。HTTP `stage`、`screening_result`、`evaluation_result`、电话和报告状态仍分别保存，不新增同名业务枚举，也不删除任何服务端记录。

| 展示状态 | 判定 |
| --- | --- |
| 简历分析 | 尚未初筛通过，包括 pending、unknown、manual_review；未知不是不通过。matched 仍需按现有入口启动深度初筛，等待或失败原因在详情查看 |
| 电话沟通 | 初筛通过后，电话等待、进行、未接通、取消、停止中或外部结果不明均在此阶段；电话已结束但报告仍生成中、失败、缺失或失效，也保留此状态 |
| 推荐报告待审核 | 电话已结束、内部评估 recommended；当前 D10 必须可读、valid、内容非空，并与该 application/job、报告版本与 artifact_ref 一致；报告为 pending_review（预览为 pending）才显示 |

明确初筛 rejected 即从岗位队列隐藏。猎头确认当前有效报告版本的审核后（approved 或 rejected），该岗位队列隐藏此人，人才档案、报告与审核历史保留。退回不代表获准交付；通过人才库或推荐审核入口仍可修订，新版本须重新审核，并重新进入岗位队列。旧报告失效或新版生成时，不得沿用旧审核确认将新流程隐藏。预览复用现有本地 reviewReport/reviseReport，仍为当前页面内存状态，刷新会恢复样例；真实审核须等待后端 B 的持久化接口，不能用本机隐藏记录冒充服务器审核。

前端 `candidateProgress.ts` 统一队列显示规则；预览标签计数及岗位卡片人数按过滤后队列计算，查看操作直达分析、电话或报告页。账号区按现有权限接口逐页读取全部岗位关联，再过滤并本地分页，避免过滤单页造成空页和总数不一致；只在报告阶段读取具体 D10 核验，失败时不标待审核。当前后端 B 尚无电话／报告审批实现，实际 application 读模型仍返回空 call_summary/report_summary，端到端验收未完成。

## 本轮状态验证

前端检查及 38 项领域测试通过，覆盖未知保留、电话各状态、空／失效／跨岗位／错误版本 D10、审批退出和新版重审。浏览器实测三状态、预览当前报告确认后退出岗位队列及人数减少、初筛未通过退出，且两种情况下人才库仍可查询；隔离 HTTP 夹具验证三页读取后过滤与计数、已审批隐藏、过期 D10 不标待审核，以及实际 D10 正文读取。未调用真实电话、报告生成或审批服务。

## 验证边界

人才列表三列调整：前端 `npm run check` 与 30 项测试通过；浏览器实测三列、三个预览查看入口及返回保留搜索条件、390px 无页面横向溢出。账号区通过隔离 HTTP 夹具验证多岗位列表、暂时无匹配及匹配中状态，未调用真实匹配模型，本次未改动 HTTP 字段或后端分流算法。

针对性测试位于 `backend/tests/test_talent_routing.py`，覆盖无岗位入库、未知保留、后端/前端分流、全栈多关联、重复与混合文件、分类版本、暂停与重新关联、发布后补关联、对象权限与受限传播、显式初筛防重、已知响应恢复、未知结果阻断，以及 PostgreSQL 并发上传。

浏览器使用独立本地数据库、虚构简历与隔离模型响应，验证登录、上传、分类、相关岗位、显式初筛、结果轮询和刷新恢复。它没有调用真实模型或搜索，不证明专业分类准确率、真实简历质量或真实电话。真实模型分类效果需使用经授权标注样本另行验收；不把构建通过、Schema 合法或关键词模拟当作真实分类效果。

本轮实际结果：PostgreSQL 容器上后端全量 **167 项通过**，包含并发与迁移检查；前端静态检查、类型检查、构建及原有 **18 项测试通过**。Ruff、五个 Schema 导出器一致性、接口虚构样例与 Git 差异空白检查通过。本地数据库已显式升级到 `0004_talent_routing`。保留现有 Starlette/httpx 弃用提示及前端大包提示；没有将它们作为功能失败，也没有据此扩展依赖或拆包改造。临时浏览器验证服务已停止，未部署、提交或推送。
